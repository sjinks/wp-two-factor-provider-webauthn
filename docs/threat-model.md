# Threat model for Two Factor Provider for WebAuthn

## Architecture and scope

This WordPress plugin adds passkeys, hardware security keys, and compatibility with legacy U2F to the Two Factor plugin. WordPress supplies the user, session, capabilities, settings, database, and cache. Two Factor selects the provider and owns the transition from primary login to an authenticated WordPress session. This plugin coordinates browser ceremonies, verifies their results through the MadWizard WebAuthn library, and persists credential records. The plugin registers its provider after schema installation and can remove the legacy U2F provider from the provider list. See `index.php:18–33`, `inc/class-plugin.php:18–57`, and `inc/class-webauthn-provider.php:220–241`.

This model is based on static review of the production PHP, shipped JavaScript bundles, configuration, legacy-data transitions, and release workflow. Existing Playwright tests document expected behavior. Runtime behavior remains unverified.

## Protected assets and actors

- **Authentication authority.** A valid primary login and a second-factor ceremony for the same WordPress user protect session issuance. Authenticator private keys remain with the authenticator. The WordPress database stores public keys, credential IDs, user handles, counters, names, and timestamps. Credential ownership and public-key integrity are security-sensitive even though public keys are public by design. See `inc/class-schema.php:65–84` and `inc/class-webauthn-credential-store.php:118–135`.
- **Enrollment and recovery.** The ability to enroll, rename, or revoke a credential is controlled by the acting user's WordPress permissions and Two Factor session policy. Revocation and migration must preserve the account owner's control and ability to sign in. See `inc/class-ajax.php:39–63,138–179,218–258` and `inc/class-webauthn-credential-store.php:141–171`.
- **Ceremony state and deployment policy.** The active challenge, expected user, expected origin, RP ID, verification settings, WordPress authentication salt, and release integrity protect the ceremony. A remote client controls its submitted response and any credentials it can legitimately use. A client with a pending login or a logged-in session has additional entry points subject to Two Factor and WordPress checks. Operators, co-resident PHP code, and release publishers exercise trusted authority as described below.

## Trust boundaries and controls

| Boundary | Effective controls and evidence |
| --- | --- |
| **Pending login → authenticated WordPress session** | Two Factor 0.17.0 resolves the pending user, validates its login nonce, selects the provider, and rate-limits attempts before calling the provider. Its login handler issues the auth cookie after provider success. The provider creates authentication options for that user's handle, takes that user's authentication context, decodes the browser assertion, and returns success after library verification. Exceptions return failure. See `inc/class-webauthn-provider.php:72–109,116–171`; locked Two Factor version in `composer.lock:4398`; local reference `vendor/wordpress/two-factor/class-two-factor-core.php:1838–1856,1899–1901,2127–2148`. Production Two Factor versions and filters are deployment dependencies. |
| **Logged-in actor → target user's credentials** | WordPress registers only authenticated AJAX hooks for preregistration, registration, revocation, and renaming. Registration nonces are scoped to the target user ID. Rename and revoke nonces are scoped to the credential ID. All four flows require `edit_user` for the target and Two Factor's `save` policy for the **acting** user's session. In Two Factor 0.17.0 an actor without 2FA enabled can update permitted options; an actor using 2FA needs a 2FA session and normally a recent proof. Site policy can change the freshness rule. Modern revocation and rename constrain the write by credential ID and the target's handle. Registration stores the handle from the verified registration result. See `inc/class-admin.php:19–29`, `inc/class-ajax.php:28–63,138–179,218–258`, `inc/class-webauthn-credential-store.php:118–171,193–209`, and local Two Factor `class-two-factor-core.php:1724–1770`. |
| **Browser assertion or attestation → server verifier** | The RP origin is derived from the HTTPS form of the WordPress home host and optional port, subject to the `webauthn_app_id` filter. `COOKIE_DOMAIN` can change the RP ID separately. The trusted `tfa_webauthn_init_server` hook can alter the server builder. The locked library checks the ceremony type, challenge, origin, effective RP ID hash, and required user flags. Assertion verification checks the credential against the ceremony's allowed credentials and user handle, verifies the signature, and handles supported counters. Registration parses and verifies the attestation and takes the registration user handle from server context. The stock builder allows none and self-attestation and trusts supported attestation without metadata, so enrollment does not establish hardware provenance. See `inc/class-utils.php:12–23,36–54` and `inc/class-ajax.php:71–89,153–179`. Library source references for the lockfile revision `99628a8` are `src/Server/AbstractVerifier.php:29–70`, `src/Server/Authentication/AuthenticationVerifier.php:34–113,148–200`, `src/Server/Registration/RegistrationVerifier.php:38–137`, and `src/Builder/ServerBuilder.php:74–97,394–421`. |
| **WordPress transient → PHP context restoration** | Authentication and registration use separate transient slots per WordPress user. The context payload has a version and a 600-second lifetime. Its HMAC binds WordPress site ID, user ID, and ceremony using a key derived from `wp_salt('auth')`. Retrieval attempts deletion and requires it to succeed, then validates the MAC, version, and time window before deserializing and checking the expected class. The code documents the non-atomic get/delete. The slot has no per-session or per-tab discriminator. Database or cache integrity and the secrecy of the salt are distinct prerequisites. See `inc/class-context-store.php:11–90`. |
| **Site policy → network-shared credentials** | The settings page uses `manage_options` and the WordPress Settings API through `options.php`; settings are read with `get_option`. User handles and credentials use `$wpdb->base_prefix` and have no site column. User handles are mapped by WordPress user ID, with cache entries backed by the shared user-handle table. Ceremony integrity is site-bound. On multisite, site policy, shared credential administration, and the browser's RP/origin restrictions are distinct boundaries. User verification defaults to `preferred`; `required` is passed to the verifier in both ceremonies. Attachment and resident-key settings are sent as registration options. The configured browser timeout is separate from the signed context lifetime. See `inc/class-admin.php:33–38`, `inc/class-adminsettings.php:28–36`, `views/settings.php:10–12`, `inc/class-settings.php:31–53`, `inc/class-settingsvalidator.php:45–67`, `inc/class-schema.php:17–31,65–84`, `inc/class-webauthn-user.php:41–81`, `inc/class-ajax.php:74–113`, and `inc/class-webauthn-provider.php:88–101`. |
| **Legacy U2F state → modern credentials** | An account with no modern rows can trigger migration from that account's legacy user metadata, including during provider availability checks. Migrated records carry the target handle and a U2F flag. Revocation deletes matching legacy metadata before deleting the modern row. A compatibility setting can rewrite the AppID extension result for a stored U2F credential; library verification then uses the configured AppID as the effective RP ID for that extension. The assertion still goes through the verifier. See `inc/class-webauthn-provider.php:138–153,178–179,202–211`, `inc/class-webauthn-credential-store.php:89–111,141–171`, `inc/class-credential-migrator.php:25–51`, and the locked library's `src/Extension/AppId/AppIdExtension.php:38–42`. |
| **Browser content → WordPress login and profile DOM** | Key names are escaped in server-rendered rows and inserted as text on rename. Profile notices use text insertion, and AJAX errors have tags stripped before transport. The login bundle uses a separate HTML insertion sink for errors, including messages that can originate from caught exceptions. A path from a remote principal to an exception message in another user's browser would require additional evidence. See `inc/class-key-table.php:52–69`, `inc/class-ajax.php:35–36`, `assets/profile.ts:78–101,229–233`, `assets/login.ts:14–19,46–56`, and the corresponding shipped bundles. Profile-notice coverage is in `tests/e2e/specs/notices.spec.ts:11–93`. |
| **Repository and dependency inputs → distributed plugin** | The tagged workflow packages committed browser bundles and installs production Composer dependencies with configured patches. It attests and publishes the GitHub ZIP; a separate job publishes through WordPress.org SVN credentials. The ZIP export and SVN deployment each exclude development files, including this model and the repository agent instructions. Publisher authority, release inputs, the Composer install and update steps, and committed bundle provenance affect every installation that receives the release. See `.github/workflows/push-tag.yml:3–18,35–58,64–101`, `composer.json:22–25,41–95`, `.gitattributes:2–21`, and `.distignore:1–22`. |

## Prioritized failure scenarios

These scenarios define the security properties to preserve and areas where deployment evidence matters.

| Priority | Scenario, prerequisite, and consequence |
| --- | --- |
| **Highest** | **Wrong account or invalid assertion accepted.** A requester who can reach a pending login and can submit a browser assertion gains the protected session only if the account, challenge, origin, RP ID, or signature binding fails. Two Factor's pending-login checks and the verifier's independent bindings are the relevant controls. Valid credentials for one account must never establish another account's session. |
| **Highest** | **Unauthorized credential enrollment or revocation.** A logged-in attacker with a stale session or delegated access gains persistent second-factor capability or causes lockout only if the effective permissions or session policy allow an unintended target or operation. Evaluate multisite delegated roles against the actual WordPress `edit_user` decision and the acting user's revalidation policy. Existing contract coverage for stale sessions is in `tests/e2e/specs/revalidation.spec.ts:40–113`. |
| **High** | **Shared credential or release integrity lost.** A principal able to alter credential rows, trusted PHP configuration, or the published package has authority over a high-impact input. The blast radius depends on shared user tables, RP and origin configuration, and how many sites consume the release. Separately, a principal with cache-write access needs a valid envelope for that site, user, and ceremony to pass the context HMAC. |
| **Medium** | **Ceremony interruption or unintended credential retention.** Concurrent attempts for the same user and ceremony share one slot. Scope the impact of overlap or replay to what a caller can reach under the Two Factor and capability gates, and to the behavior of the deployed transient backend. On legacy accounts, concurrent migration and revocation or partial storage errors can threaten the invariant that a revoked credential stays revoked; source shows cleanup ordering, while atomic behavior across metadata and credential storage remains unverified. |
| **Conditional** | **Script execution through a login notice.** The login bundle's HTML error sink makes remote influence over a victim-visible message the key prerequisite. The profile tests cover a different sink and its text rendering. Severity depends on reachable input, the victim flow, and the privileges present on the affected origin. |
| **Conditional** | **Incomplete cleanup on multisite uninstall.** Schema setup uses the base prefix and the site-option API, while uninstall uses the current prefix and the ordinary option API. The guarded uninstall path also removes older context user metadata, while active contexts have a short transient lifetime. Verify which data survives the actual WordPress uninstall context before making claims about cross-site reach or retained records. See `inc/class-schema.php:17–31,47`, `uninstall.php:14–25`, and `inc/class-context-store.php:11–33`. |

## Assumptions and verification limits

- Production is assumed to use a supported WordPress and Two Factor installation, working HTTPS, correct external URLs and proxy configuration, and trusted PHP extensions and plugins. Login presentation checks `is_ssl()`; the profile template warns about HTTP and the browser controls access to its WebAuthn API. Origin and RP ID enforcement occurs in the server verifier. See `inc/class-webauthn-provider.php:72–78` and `views/user-profile.php:19–25`.
- `composer.lock:699` pins MadWizard WebAuthn v1.1.0. The verifier references above point to the locked upstream source. Project patches were reviewed separately. Installed production versions, final packaged bytes, optional hooks, proxy and multisite topology, and cache concurrency behavior were not verified.
- These priorities concern possible impact and prerequisites. See the [security policy](../SECURITY.md) for reporting and dependency scope.
